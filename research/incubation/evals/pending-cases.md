# Обязательные случаи без достаточного incident evidence

**Это не observed eval corpus.** Пользователь просил рассмотреть эти случаи; источники подтверждают важность проверки, но не все реальные сбои. P-карточки нельзя учитывать в числе девяти наблюдавшихся сценариев из [catalog.md](catalog.md).

R/S — [реестр источников](../evidence/source-register.md). Будущие проверки здесь предложены, не выполнены. Если позже строится искусственный bad fixture, он помечается induced counterexample, а не исторический инцидент.

## P-01 — Native SLOT exists, visible content is not owned by it

- **Scenario:** потребитель вставляет custom content в открытую область и заменяет его штатной slot-операцией.
- **Representative bad state:** внутри master есть пустой native SLOT, но видимые label/иконка/список размещены sibling-узлами рядом. По виду всё похоже на наполненный слот.
- **Почему выглядит правдоподобно:** type === SLOT, property зарегистрирован, manifest содержит slotId; статичный снимок показывает ожидаемое содержимое.
- **Observable failure при будущей пробе:** замена/удаление содержимого SLOT не заменяет/не удаляет то, что пользователь считает slot content; скрытие области не действует на внешний контент; inherited layout меняется отдельно.
- **Pass condition:** структурный ownership trace от содержимого до правильного Slot и реальная замена в consumer instance дают один и тот же результат; нет внешнего дубля, прежний контент ушёл; master и другое применение сохранились. Одного node.type недостаточно.
- **Какое evidence породило вопрос:** R-08 содержит type-only check; R-04 задаёт свободную область. S-03 показывает настоящий CSV **внутри** Slot и дефект fill, не wrong ownership. R-02 описывает успешную замену, а не отрицательный пример.
- **Core/adapter:** Figma adapter; семантика ownership — core promotion candidate.
- **Статус:** **точный incident не найден**. Нужен записанный consumer operation и tree до/после. Нельзя подменять этот случай FRAME с именем slot из стороннего референса.

## P-02 — Common edit requires detach / private traversal

- **Scenario:** человек/агент без истории автора меняет предусмотренную контрактом подпись, иконку или свободную область.
- **Representative bad state:** нужный контроль спрятан в непубличном вложенном master; инструкция требует detach или угадывать внутренний путь узла.
- **Почему выглядит правдоподобно:** автор знает дерево и быстро делает правку; компонент выглядит переиспользуемым в его собственной витрине.
- **Observable failure при будущей пробе:** независимый потребитель не может завершить предусмотренную операцию через публичный instance, явно exposed часть или штатный canvas Slot; вынужден разорвать связь/править private internals.
- **Pass condition:** операция выполнена по имени и description через заявленную поверхность; master linkage сохранён; нет ручной реконструкции. Canvas Slot и явно exposed nested properties допустимы. Новое требование вне контракта не является автоматическим FAIL.
- **Какое evidence породило вопрос:** R-04/R-06 задают будущую DX-приёмку; R-02 признаёт её отсутствие. S-04 показывает API-ошибку expose внутри Slot, но **не вынужденный detach потребителя**.
- **Core/adapter:** core candidate о discoverability; конкретная поверхность редактирования — Figma adapter.
- **Статус:** **точный incident не найден**; author smoke не заменяет независимую пробу.

## P-03 — Master change destroys consumer overrides

- **Scenario:** два consumer instances имеют разные texts, icon swaps и custom Slot content; master получает осмысленную общую правку.
- **Representative bad state:** автор пересоздаёт внутренние узлы или меняет структуру при обновлении; после update потребитель теряет своё содержимое/локальную настройку.
- **Почему выглядит правдоподобно:** master после правки выглядит лучше и технически корректен; проверяется его витрина, не ранее настроенные consumers.
- **Observable failure при будущей пробе:** общий стиль обновился, но text/swap/slot override сбросился, исчез или изменил соседний consumer.
- **Pass condition:** записать ожидание общего изменения и локального инварианта до операции; сравнить оба consumer instances после изменения и обновления зависимости. Text overrides, instance swaps, Slot content сохраняются; допустимое изменение контракта явно отделено от совместимой правки.
- **Какое evidence породило вопрос:** R-06 предписывает именно эту операцию; R-02/R-03 сообщают незакрытую DX. В референсе были переименования слоёв (R-11), но запись о фактическом сбросе override отсутствует.
- **Core/adapter:** core promotion candidate; механика master update — Figma adapter.
- **Статус:** **точный incident не найден**; успешной mutation-пробы тоже нет. Переименование слоёв само по себе не доказывает потерю данных.

## P-04 — Technical gates green while UX/DX remains unverified

- **Scenario:** принимающий смотрит зелёный технический отчёт и объявляет библиотеку или экран готовыми.
- **Representative bad state:** все предусмотренные для среза technical checks зелёные, но нет операций независимого consumer и доменного пользователя; отчёт смешивает три группы evidence в один PASS.
- **Почему выглядит правдоподобно:** структурные проверки воспроизводимы, дают числовой результат и кажутся более объективными, чем UX/DX-наблюдение.
- **Observable failure при будущей пробе:** заявлена UX/DX-готовность без фактической операции/наблюдения либо consumer не может редактировать или понять композицию, несмотря на technical PASS.
- **Pass condition:** технический результат сохраняется в своём scope; незапущенные UX/DX явно остаются unverified и блокируют соответствующее утверждение о готовности. Полный PASS возможен только с отдельными результатами требуемых consumer/domain операций.
- **Какое evidence породило вопрос:** R-08/E-04 подтверждают false-green локальных gate algorithms; R-02/R-03 подтверждают отсутствие независимой UX/DX. **Документированного события «все live technical gates green» на этой же ревизии нет.**
- **Core/adapter:** core candidate; конкретные технические gate scripts — adapters.
- **Статус:** **частично подкреплён, полный составной incident не установлен**. Его нельзя задним числом достроить из отдельных фактов.

## P-05 — Wrong public/private/local component boundary

- **Scenario:** выбрать повторяемую часть и проверить, какие изменения должны распространяться, а какие принадлежат одному экрану.
- **Representative bad state:** либо общий инвариант скопирован локально и дрейфует, либо экранная композиция опубликована как общий master и требует флагов под каждое применение, либо private atom ошибочно требует самостоятельного API.
- **Почему выглядит правдоподобно:** повторение принимают за доказательство public, экранное имя — за доказательство local; число instances или наличие Storybook story используют вместо ownership.
- **Observable failure при будущей пробе:** intended common change не достигает всех применений; local change меняет соседний сценарий; обычное редактирование требует новых экранных флагов/разрыва master, хотя операция входила в исходный контракт.
- **Pass condition:** объяснены semantic purpose, владелец изменения и consumer operation; common и local edits выполнены в двух содержательных применениях. Не нужна публичность каждой повторяемой детали, а продуктовая специализация не запрещает её автоматически.
- **Какое evidence породило вопрос:** R-03/E-08 — реальная переделка слишком жёсткого правила; R-10/E-09 — дрейф референса. R-06 содержит критерий. Failed import header из R-02 — недостаток канала, не доказательство неверной public/private классификации.
- **Core/adapter:** core promotion candidate; Figma public/private/local representation — adapter; политика публичных exports — Haulplane.
- **Статус:** **reference/review evidence есть, полного Haulplane mutation incident нет**. Не выдавать E-03 file placement за доказательство всех трёх component-boundary ошибок.
