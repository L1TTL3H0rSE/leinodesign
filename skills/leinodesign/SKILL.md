# LeinoDesign

Экспериментальный навык. Создавай дизайн, который работает с настоящим
содержимым и остаётся редактируемым. Техническая корректность, визуальное
качество, удобство редактирования и поведение реализации — отдельные выводы.

## Установи контекст

Из поручения и доступных источников определи:

- задачу пользователя продукта, нужные данные, действия и состояния;
- режим: отразить существующую реализацию, предложить новый дизайн,
  изменить оформление с сохранением контракта или проверить результат;
- целевой файл/область, исходные компоненты и токены, статус решений;
- язык интерфейса, характер содержимого и значимые размеры/ширины.

Не проси повторять уже доступные сведения. Рутинные решения принимай сам в
разрешённом объёме; существенные неизвестные назови. Для пробы без реальных
данных используй правдоподобные синтетические и укажи происхождение вне UI.
Принятое решение отличается от работающего примера и от нового предложения.
Наличие значения в коде само по себе не делает его принятым дизайном.

Сначала осмотри источник и текущие артефакты. При точном отражении кода
сохраняй его контракт; при редизайне записывай намеренные отличия. При
проектировании без кода предложи контракт явно. Не сужай публичные возможности
ради удобства инструмента. Навык не меняет разрешения проекта и пользователя.

## Собери небольшой законченный фрагмент

1. Назови главное решение пользователя и нужный для него контекст. Из них
   выведи группировку и визуальные приоритеты. Не начинай с готового набора
   «карта + карточки + панель», если задача его не объясняет.
2. Найди подходящие существующие компоненты и стили. Используй связанные
   экземпляры; несовместимость объясни конкретной операцией или контрактом.
   Локальная композиция допустима. Повторяемость и экранное имя не определяют
   публичность автоматически.
3. Для компонентов прочитай [контракт и изменения](references/components.md).
   Выбирай свойства по операциям потребителя; открытое содержимое не кодируй
   перечнем вариантов. Создавай только нужные сочетания, отмечая непоказанные.
4. Для Figma прочитай [адаптер](references/figma.md) и актуальные инструкции
   доступного инструмента. Механику API проверяй там, не угадывай по этому навыку.
5. Примени выбранные токены и стиль к содержательному примеру. Авторские
   заметки, происхождение данных и критерии проверки держи вне продуктового
   фрейма. Пользовательские ограничения, единицы и сообщения об ошибках сохрани.
6. Проверь результат по [визуальному просмотру](references/visual-review.md),
   исправь причину обнаруженной ошибки и повтори ту же проверку до расширения.

## Проверь использование, а не только наличие

Для новой или существенно изменённой границы компонента создай независимые
применения с разным содержимым. Выполни предусмотренную локальную правку,
изменение размеров и общее изменение master. Запиши, что должно измениться
и что сохраниться; проверь текст, swaps и свободное содержимое у потребителей.
Не выдавай чтение дерева за испытание изменения. Авторская проба полезна,
но не заменяет работу потребителя без истории создания, если заявлена такая DX.

Автоматическая проверка сравнивает с ожиданием из входного контракта, а не с
манифестом, переписанным с готового артефакта. Проверь конкретные значения,
связи и каждый включённый вариант. Пустой набор проверок — не PASS.
Если добавляешь проверяющий код, покажи, что он отвергает целевой дефект по
ожидаемой причине и принимает исправленный контроль. Один ненулевой exit code
не доказывает обнаружение: ошибка запуска или безусловный отказ теста не считаются.
Проверяй также конечное состояние после восстановления. Искусственный дефект создавай в пробе,
а не в чужом или рабочем продукте.

## Передай результат

Сохрани ссылки/IDs, снимки выбранного контекста, операции и фактические
результаты. Кратко раздели: технически проверено; визуально просмотрено;
проверено редактированием; проверено в реализации/с пользователем.
Невыполненное пометь `not run`, неизвестное — `unknown`; не превращай их
в успех. Для незавершённой работы оставь конкретный следующий шаг.

Не вводи обязательные квоты страниц, компонентов, вариантов, токенов,
пользователей или ширин. Не добавляй публикацию, установку навыка, перенос
источника истины либо синхронизацию с кодом, если этого нет в поручении.
